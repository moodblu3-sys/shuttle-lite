# Cursorへの依頼文：Snowflake接続のセットアップ

以下をCursorに渡す。実際のアカウント情報・鍵・パスフレーズはこの文書に追記しない。

---

このMacのShuttle Liteを、実行ログの送信先であるSnowflakeに接続してください。
実装を作り直すのではなく、既存のSQL API・キーペア認証・設定画面を使って疎通を確認する作業です。

## 1. 作業場所と実装の確認

- 実際に起動しているshuttle-liteの作業ディレクトリー、ブランチ、未コミット変更を確認してください。
- GitHubのmainにある専用の新規移行画面とSnowflakeの「テストログを送信」が入っているか確認してください。
  古ければローカル変更を保ったまま取り込んでください。reset --hard、clean、DB初期化はしないでください。
- まずdocs/settings.md、packages/telemetry/src/snowflake.ts、設定APIを読み、現在の項目と動作を確認してください。
- 既存のBox認証・プロキシ・CA設定を変更しないでください。作業中の移行を止めないでください。

## 2. 接続先と権限を用意

アカウント識別子、接続ユーザー、ウェアハウス、データベース、スキーマ、実行ロールについて、
既存の利用可能なものを確認し、不足項目だけ私に聞いてください。
勝手にウェアハウスの新設・サイズ変更をしないでください。
CursorからSnowflakeを操作できない場合は、私がSnowsightで実行するSQLと操作順を作ってください。

ログ専用テーブルは次の列構成に合わせてください。実際のデータベース・スキーマを明示したSQLにしてください。

```sql
CREATE TABLE IF NOT EXISTS SHUTTLE_LITE_EVENTS (
  EVENT_ID VARCHAR NOT NULL,
  JOB_ID VARCHAR NOT NULL,
  PAYLOAD VARIANT NOT NULL,
  LOADED_AT TIMESTAMP_LTZ DEFAULT CURRENT_TIMESTAMP()
);
```

同名テーブルがある場合は列を確認し、不適合なら別名の専用テーブルを用意してください。
CREATE OR REPLACEや既存データ削除はしないでください。
実行ロールに対象ウェアハウス・データベース・スキーマのUSAGEと、対象テーブルのSELECT・INSERTを付与してください。
ログ送信用ユーザーにそのロールを割り当て、アプリからそのロールを指定してください。
アプリ用にACCOUNTADMINを使わないでください。

## 3. キーペア認証

公式手順と既存ユーザーの設定を確認し、RSA 2048bit以上・PKCS#8 PEM形式の鍵を使ってください。
鍵がなければリポジトリ外の専用ディレクトリーに生成し、秘密鍵を600権限にしてください。
既存の鍵ファイルや登録済み公開鍵を上書きせず、このアプリ用の公開鍵を登録してください。
暗号化鍵のパスフレーズは私がローカルで入力し、チャットやコマンド引数へ貼らせないでください。

Macの.envには、必要な次の項目だけを設定してください。

```dotenv
SNOWFLAKE_PRIVATE_KEY_PATH=/absolute/path/outside/repository/rsa_key.p8
SNOWFLAKE_PRIVATE_KEY_PASSPHRASE=
```

パスフレーズは暗号化鍵のときだけ設定します。
.env全体、秘密鍵、JWT、Authorizationヘッダーを表示・ログ出力・コミットしないでください。
変更後、実行中の移行がないことを確認してwebとworkerを再起動してください。

## 4. アプリの設定と接続確認

OAuth利用時は、ログイン中の本人のBoxユーザーIDが `SHUTTLE_ADMIN_USER_IDS` に含まれるか確認してください。
未登録なら、既存の管理者IDを保持して本人のIDを追加してください。全ユーザーを管理者にする変更はしないでください。
環境変数変更後は、移行の実行中でないことを確認してweb・workerを再起動してください。

設定画面の「管理者設定」で「処理ログ」をSnowflakeにし、アカウント・ユーザー・ウェアハウス・
データベース・スキーマ・テーブル・ロールを入力して保存してください。
保存済みの画面設定が.envの初期値より優先される点に注意してください。

保存後、「テストログを送信」を1回押してください。合成イベントを1件送る操作で、Box転送はありません。
成功表示だけで終わらず、画面に出たevent IDを使い、同じ接続先のテーブルを検索してください。
SQL中のテーブル名は実際のデータベース・スキーマを含め、event IDは実測値に置き換えてください。

```sql
SELECT EVENT_ID, JOB_ID, PAYLOAD, LOADED_AT
FROM SHUTTLE_LITE_EVENTS
WHERE EVENT_ID = '<画面に表示されたevent ID>';
```

1件の保存を確認してください。プロキシを使う構成ならSnowflakeホストへの通信も確認し、
エラーを直すために必須プロキシやTLS検証を無効化しないでください。
失敗時は鍵の対応・アカウント識別子・ロール・テーブル構成・通信を切り分け、秘密を伏せて原因を報告してください。

## 5. 通常の自動送信の確認と報告

接続テストはwebからの送信なので、それだけでworkerからの自動送信確認済みとはしないでください。
私が次にデモ移行を実行したら、そのJOB_IDでSnowflakeの行が増え、
アプリのログ送信待ちが解消することを確認する手順を用意してください。
今回のセットアップだけでBoxへのアップロード・承認・再実行・削除はしないでください。
未送信イベントはworkerが再送しますが、過去にローカルへ送信済みのログは自動で移し替わりません。

最後に、設定した非秘密の接続先・テーブル、web/workerの起動状態、テストevent ID・保存時刻、
残っている手作業を報告してください。できていない操作を完了扱いにしないでください。

OAuth方式の移行には認証済みBoxユーザーID・操作種別・ファイル名・配置先IDの監査情報が含まれます。旧CCG方式の移行に本人確認済みIDは後付けされません。今回の設定作業ではpayloadを変更せず、実測した送信内容だけを報告してください。
